# Map actual work before automation

A refund process has an approved procedure, operator interviews, and recent tickets. The goal is first to understand current state, not redesign it.

```text
procedure + interviews + ticket examples
  → map-the-work
  → documented vs evidenced vs reported behavior
  → handoffs / queues / tacit rules / rework
```

The map shows that the documented manager approval occurs only above a threshold, tickets often wait in an unowned queue, operators reconcile two systems in a shadow spreadsheet, and missing bank details cause re-entry. Each claim is labeled confirmed, reported, inferred, or unknown.

Only if the next goal is automation does the sequence continue:

```text
map-the-work
  → find-the-exceptions, if material branches remain unclear
  → automate-this, if an executable future state is requested
```

Neither follow-on is mandatory: a current-state map can itself be the finished outcome.
